## What this is

Koil is a Rust (edition 2024) library for editing directories as a list of entries, in the style of `vidir`/`oil.nvim`. A frontend gets the entries of the open dir (`Koil::listing`), lets the user edit them, and hands them back (`Koil::update`). Koil diffs the edit against the filesystem to produce a list of `Action`s (create, delete, rename, copy), which the frontend shows and then applies once the user confirms.

This crate is **library only**, and it is never used by users directly. The CLI is the sibling project `../koil-cli`, and a GUI is planned. The text listing format, sqids IDs, the session files and shell commands all live in the CLI. The library takes and returns Rust data, so **all logic lives here**, and frontends only present it. The library works in two phases so a frontend can confirm in between: preview (`Koil::compute_actions`, `Koil::changes`, `Koil::undo_steps`, `Koil::undoable`), then act (`Koil::apply`, `Koil::apply_only`, `Koil::undo`, `Koil::undo_only`, which return a `Report` or a typed `KoilError`), or take changes back without acting (`Koil::discard_only`).

What the GUI expects, so keep the API fitting it:

- It has a path field (`Koil::location`), a separate settings section (later things like showing hidden files), and navigates with `Koil::update_and_open` (or `Koil::open_with`, its settings and a location, when no listing is shown to read).
- It hides IDs, but shows names, and colors dirs differently (`Entry::is_dir`). It shows them as text, which a name that is not Unicode can only be shown in with `�`, and reads its lines back with `Koil::read_shown`.
- It highlights the line an error (and later, a warning) is about, so problems must point at an entry (`EntryError::entry` is the index into the entries given to `update`), not just say that something is wrong.
- It shows the actions to confirm, like `MOVE a -> b` / `CREATE new` (it matches on `Action`, and `Display` gives `move a -> b`), and user can leave some of them out for later (`Koil::changes`, `Koil::apply_only`), or take some back (`Koil::discard_only`).
- It opens a new file to write in it, after asking to create it then and there, keeping the other changes (`Koil::create_steps`, `Koil::create_now`), and so a copy (`Koil::copied_from`), and makes the copies of a file before user changes it (`Koil::copies_of`).
- It needs the name of an entry from just its ID (`Koil::path_of`, and `Koil::id_of` the other way), and paths relative to the open dir (`Koil::relative`).
- It marks the entries that applying would change (`Koil::is_pending`: new, or not at their ID's path).
- It sorts the listing as user picks (`Settings::sort`), shows what it is sorted by after each line (`Koil::metadata`: a size, a date), and puts an entry that changed on disk where the listing would have it (`Koil::compare`).
- It watches the open dir and shows what changes on disk right away, keeping the user's edits (`Koil::sync`, `Koil::watched`), and asks about what goes against them (`Conflict`, `Koil::resolve`).

## API

- **`Entry { id: Option<Id>, name: PathBuf, is_dir: bool }`** is one line. `id: None` is a new entry to create. `name` is relative to the open dir and can be a nested path (`dir/A`) in `update`, but `listing` only gives plain names (nested ones in a pattern view). Names that `listing` and errors give only have `/`, also on Windows (`Koil::name`, `with_slashes`, which is public so frontends show their paths the same way), as users write it, and so do the paths in every message (`shown`: `OpenError`, `Warning`, `Action` and `Undo`'s `Display`, and the io errors of apply and undo); `\` in a name from `update` is still a separator there. A name that is not Unicode (only on Linux, or a malformed one on Windows) can only be shown as text with `�` (`to_string_lossy`), and read back so, it would be a rename to that: a frontend reads its entries back with `Koil::read_shown`, which takes each part of a name that is how the part of its ID's path in the same place from the end is shown for that part (from the end, so `dir/a�` is `a\xff` moved into `dir`, and a pattern's `d�/f` is in `d\xff`). `update` takes names as they are, as `sync` gives back the entries it was given, which a frontend finds its lines by. `is_dir` only matters for new entries in `update`.
- **`Id(pub u64)`** is an opaque, stable handle: an index into `Koil::ids`. It never starts pointing to a different file, but it follows its file when `sync` sees it renamed or moved on disk (`ids[index]` changes then, and nowhere else). Frontends can show it however they like (the CLI encodes it with sqids).
- **`Koil::listing() -> Vec<Entry>`** merges the real directory contents with pending diff state, so entries renamed or moved into this dir show up there. Existing entries come first (dirs, then files), then new ones, each sorted by `Settings::sort` (see Sorting). It never has `..`, even with `show_hidden`: a frontend opens the parent dir with `open`, and `..` written in `update` is an `InvalidName`, as is any `.` or `..` part (see Entry names).
- **`Settings { show_hidden, respect_gitignore, regex, sort }`** (`Koil::settings`, `Koil::set_settings`, which reopens the dir, or the builder's `.settings(...)`) controls how the listing is shown, and is saved with the state. Hidden entries (names starting with `.`) are left out of `current_listing` by `open`, unless they have pending changes in the diff: `update` takes every entry of `current_listing` that is missing as deleted, so a changed entry must stay, or hiding it would turn a rename into a copy and forget a delete. Entries in the diff are always shown, even hidden ones. `respect_gitignore` (off by default) hides what git ignores and the `.git` dir, and works the same way: changed entries stay.
- **Walking** (`Koil::walk`, with `ignore::WalkBuilder`) reads both views: depth 1 for a dir, for a glob unlimited with `**`, else the glob's part count, and always unlimited for a regex. It filters hidden entries (`.hidden(...)`), except for a glob with a part that starts with a `.` (see Patterns): that walk has them all, and `Dots::walks` says which to take (on Windows it skips one that its attributes hide, `hidden_attribute`, as `ignore` does, unless its name starts with `.`). With `respect_gitignore` it reads `.gitignore`, `.git/info/exclude`, the global excludes, and `.gitignore` files of parent dirs up to the repo root; like git, nothing is ignored outside a repo (`require_git` is left on). ripgrep's `.ignore` files are never read. The open dir itself is always read, even if it is hidden or ignored, and unreadable dirs inside it are skipped. It runs on many threads (`build_parallel`), so the paths are sorted after, and new IDs are given in that order. A pattern's walk does not enter a dir that nothing inside can match (`Prune`, `WalkState::Skip`): `Matcher::dfa` is the matcher's regex as a dense DFA (a glob's from `Glob::regex`, as bytes with `.` matching a new line, like globset), and a dir is skipped when, after its text (`match_text`, `/` included), every next byte leads to the dead state. A DFA over `DFA_SIZE_LIMIT` is not built, and then nothing is skipped. A pattern also stops (`WalkState::Quit`) when it goes over `Limits` (matches, or paths searched, on `Koil`, set with the builder): `open` then fails with `OpenError::OverLimit` and changes nothing (it opens in a clone of `Koil`), and `reopen` (settings, refresh) opens the base dir instead, with `Warning::OverLimit`. A plain dir has no limits. `list` finds known paths' IDs in a `HashMap`, since `ids.iter().position` per path is quadratic with thousands.
- **Sorting** (`Sort { by: SortBy, reverse }`, `Koil::compare`, `Koil::metadata`): `listing` is the dirs with IDs, the files with IDs, then the new entries, each sorted by `SortBy` (`Name`, the default, as bytes compare; `Natural`, ignoring case, with numbers by value; `Extension`; `Size`, a dir's being how many entries it has; `Disk`, the space on disk, a dir's being how many entries it has too; `Modified`, `Created`, `Accessed`), each in the order people usually want first (A to Z, biggest or newest first), then by name. `reverse` turns the order within each group around, but not the groups. `dirs_first` (on by default, so `Sort` has its own `Default`) can be turned off, and then the dirs and files with IDs are one group (`1/`, `2.txt`, `3/`); by `Size` or `Disk` the dirs then go after the files (by how many entries they have), as a dir's size is not known here, which `reverse` turns around too, and a frontend that counts dirs' sizes puts them among the files. New entries have nothing on disk, so by what `SortBy::reads_metadata` they are sorted by name. What it reads (`Metadata`: `is_dir`, `size`, `entries`, `disk_size`, the three times) comes with the walk, on its threads (`Seen::meta`, from `item.metadata()`, which it already read for `FileKey`), and a dir's `entries` (a `read_dir`, hidden ones only with `show_hidden`) only when sorting by size or `Disk`, as it costs a read per dir. `disk_size` (only when sorting by `Disk`) is the public `disk_size`: the blocks in the metadata on Unix (`st_blocks` × 512, so a sparse file takes less than its size, a small one a whole block), but on Windows the walk's metadata (the directory's find data) has no allocation size, so it opens the file (as `same_file` does) for `FILE_STANDARD_INFO::AllocationSize` (`windows-sys`), much slower than the walk itself; frontends that count a dir's size on disk use it too. `Koil::metadata(id)` gives it from `seen` for an ID in `current_listing` (as of the last read; `sync` reads it again), else from disk now (an ID from another dir, written here). `listing` reads it once per entry, not once per comparison, and only if `reads_metadata`. `Koil::compare(a, b)` is the same order, for frontends to put an entry where the listing would. Changing the sort goes through `set_settings` (reading the dir again, with the counts), and does not make `Updated::moved` true, as it shows the same entries.
- **`Koil::update(&[Entry]) -> Result<Vec<EntryWarning>, UpdateError>`** changes nothing if any entry is invalid, and returns every problem as `EntryError { entry, kind }` (`UnknownId`, `InvalidName`, `Duplicate { path, first }`, `NotADirectory`, `AlreadyExists`, `IntoItself`, `IntoDeleted`, `NameTooLong`, `ControlCharacter`, `WindowsName`, `NotOnDisk`), sorted by entry. `NotOnDisk` is an ID whose path is gone from disk (only checked for IDs not in `current_listing`, which were on disk when read): a line pasted from a register, or one undo brought back, after its file was deleted; it used to fail halfway through an apply. Names that work but are not recommended give `EntryWarning { entry, kind }` (Windows characters, shell characters, Windows reserved names, emoji, invisible or look-alike characters, a space at an edge, a trailing `.`, a leading `-`, not UTF-8); they are returned when it works, and in `UpdateError::warnings` when it does not. On Windows itself, the ones about names Windows can not use (its characters, reserved names, a trailing `.`) are errors instead, `EntryErrorKind::WindowsName` (`names::on_this_os`): there they fail halfway through an apply, or make something else (`a.txt:b` writes a hidden stream of `a.txt`). `Koil::check` returns the same without changing anything, so a GUI can show problems while user types.
- **`Koil::update_and_open(entries, settings, location)`** is what a frontend does with an edited listing: `update`, then the settings, then `open` the location if there is one, on a clone, so if any of it fails (`UpdateOpenError::Update` or `Open`) nothing changes. The order matters: the entries must be read with the settings they were listed with, as `update` takes every listed entry that is missing as deleted (read with `show_hidden` just turned on, a listing without the hidden entries would delete them all). With a location, the settings are set without reading the open dir again, as `open` reads with them. `Koil::open_with(location, settings)` is that without the entries, for a frontend that has no listing to read (it shows a file); `set_settings` and then `open` would read the open dir for nothing first. `Updated::moved` says whether the listing shows other entries now (`Koil::shows`: the dir, the pattern, `show_hidden` and `respect_gitignore`, not `regex`), so a frontend shows it as a new listing rather than as an edit of the old one.
- **`Koil::complete(location, settings)`** is for a frontend's path field, to complete a location being written (up to the cursor) like a shell: `Completion { dir, start, part, names }`, the dirs (each with a `/`) the last part (after the last `/`, as read: `part`) can be the start of, in the dir before it, read with `read_location` (nothing if that is not a dir or is a pattern), or `current_dir` without a `/`. `start` is where the part is written, which a name replaces. They are the dirs on disk (`dirs_in`, a depth 1 walk with the same `walker` as `walk`, so hidden ones only with `show_hidden` or a part that starts with `.`, and no ignored ones with `respect_gitignore`), the new dirs in the diff (which `open` can open), and `..` for `.` or `..`; if none of them starts with the part, the ones that have its characters in order (`has_in_order`, as zsh's fuzzy `r:|?=**` matcher, which Zim sets after a case-insensitive prefix one: `myt` gives `my_tools`, `own` gives `Downloads`); case is ignored unless the part has an uppercase letter (smart case, like vim's `smartcase`), so `k` gives `Koil` too, and `K` only it. Names are written as they are, since a location that is a dir as written always opens as one. Nothing completes for a part that starts inside quotes (the last `/` is quoted). The `~` alone completes to `~/`. On Windows, the dirs in the drives are the drives' names (`C:/`, `drive_names`), and a part with no `/` before it that is a letter, or a letter and a `:` (`starts_drive`), also gets the drives wherever it is written (`t` gives `T:/` with the dirs starting with `t`; the tests' `completed` leaves them out, as the CI runner's `D:` would be among `d`'s).
- **Drives** (`drives.rs`, only on Windows, where nothing is in a dir above the drives' roots): the drives are a listing of their own (`Koil::shows_drives`), whose `current_dir` and `location` are `/` (`DRIVES`): a root without a drive, which Windows itself reads as its current drive's root, but koil as above every drive, so `resolve` makes `..` of a drive's root (`is_drive_root`, `C:\`) the drives (Windows' own `GetFullPathNameW`, which `std::path::absolute` calls, takes `..` away as written, so a path with a root skips it there: `absolute`), and a name in them a drive's root if it is one (`/C:` is `C:\`, `drive_root`), else a path nowhere (`/x`, which `in_drives` tells, and `on_disk`, `Koil::is_dir` and `not_a_dir` never look for on disk; `in_drives` is public, for a frontend's own lookups). `Koil::joined` joins a location to the open dir for `read_location`: a drive's name alone (`C:`) is its root (Windows would read it as the dir it was last in on that drive), a path with a root but no drive is in the drives wherever it is read (so `/` opens them from anywhere, rather than the open dir's drive), and in the drives a relative path is read in them (`C:` is `/C:`). The listing (`read_drives`, `GetLogicalDrives`, so also a drive with no disk in it, a dir whatever it is) names each root as its drive (`C:`, `drive_name`, which `name` and `relative` use there: `C:/x` for a path on it), reading what is there only when sorting by it (a network drive that can not be reached is slow). `update` there (`update_drives`) changes nothing: a drive left out stays (there is no entry to point at), and a drive renamed (`EntryErrorKind::Drive`), written twice, anything else (`NotADrive`), or a new entry at a drive's name (`AlreadyExists`) is an error; a drive's ID written in any other listing is `Drive` too, as it can not be moved or copied. `sync` there (`sync_drives`) adds the drives that came and removes the entries of those that went, `watched` is nothing, `dirs_seen` is empty, a pattern there is `OpenError::PatternInDrives`, and `not_a_dir` of a drive that is there but can not be read is `OpenError::Io` (no disk in it). On Unix `is_drives`, `in_drives` and `drive_root` are false or `None`, so none of it runs. Its tests are `#[cfg(windows)]` (`test_drives*`, `test_complete_drives`), which CI runs on Windows; `cargo check --target x86_64-pc-windows-msvc --tests` type-checks them elsewhere.
- **Name checks** (`names.rs`, `names::check` for one part of a path) only run on parts of written paths that do not exist on disk yet (`Koil::new_names`), so existing weird names never warn, and an unchanged entry is never checked. `AlreadyExists` (`Koil::taken`) catches a create or rename onto something on disk that is not deleted or moved away in the diff, like a hidden or ignored file, a file outside a glob, or a name that only differs in case on a case-insensitive filesystem (`apply::same_file`: device and inode on Unix, volume serial and file index on Windows, compared with `same-file`, of the link itself in both, as `same_file::is_same_file` follows links and opens files to read them, which waits forever on a named pipe); a rename that only changes case, and `dir/` over an existing dir (`mkdir -p` does nothing), are fine. It is also what is written at a path the diff already creates where the listing does not show it (`elsewhere` in `update_entries`: in another dir's listing, or as a nested name like `dir/A`, which no listing of the open dir shows), as applying would make one and fail halfway at the other (the planner orders two creates of one path without complaint, and `Action::run` never overwrites); the same ID, or a new entry written there again, is the same create. A file that is not on disk where something written elsewhere is inside is `NotADirectory` (`around_elsewhere`), as is a parent that the diff makes a file (`check_parents`). These checks go by `Diff::outcome` (`Outcome`: the files it makes, the dirs it deletes, where it renames each path), since only `update` can point at an entry. `IntoDeleted` is an entry new, copied or moved into a dir the diff deletes (also through a dir moved into it, `Outcome::carried`), which would go to the trash with it right after it is made; what is written in a dir first, and the dir deleted in a later update, has no entry to point at, so it goes to the trash with the dir, which is what deleting it means. `IntoItself` (`apply::inside`) catches a dir copied or moved to a path inside it (also one that only differs in case, as `same_file` compares the parents that exist); `Action::run` checks it too, since `copy` would copy the new copy into itself again, until the path is too long, and a move fails halfway through an apply. A symlink to a dir is copied or moved as a link, so it can go inside that dir. It also catches a dir moved into itself through other moved dirs (`A` to `B/A`, `B` to `A/B`, which goes with the dir it is in again and again: `Outcome::carried` of its rename target goes inside it), in one listing or across several; a copy is made before the dirs move, so it never does. It never navigates. Frontends call `open` afterwards (the CLI does it for `>` and the header).
- **`Koil::open(location)`** navigates, and never changes the diff. `location` is a dir or a pattern (`Pattern::Glob`, or `Pattern::Regex` when `Settings::regex` is on). It can open a new dir that is pending in the diff (`Diff::creates_dir`). If the path (or the glob's base dir) is not a dir on disk or pending, it fails (nothing changes), naming its first part that is not a dir: `OpenError::NotADirectory` if that is a file (on disk or new in the diff), else `OpenError::NotFound`. It also fails with `OpenError` `Io`, `InvalidGlob`, `InvalidRegex` or `OverLimit`. Only reading what is open again falls back (`read_or_fall_back`, used by `reopen` and `sync`): if the open dir is gone (after an apply), it opens the closest ancestor that is a dir, with `Warning::DirNotFound`, and if the pattern goes over `Limits`, its base dir, with `Warning::OverLimit`. `open` reads the location (`read_location`, public so a frontend can find the pattern in what user is typing; `resolve` canonicalizes it with `dunce`, so on Windows it has no `\\?\`, which frontends would show and where `/` is not a separator), then sets the dir and pattern and reads them (`read_listing`); `reopen` (used by `refresh` and `set_settings`) reads the stored `Pattern` again, so turning `regex` on or off never reinterprets what is already open, only the next `open`.
- **Patterns** (`globset` and `regex`, compiled by `Pattern::matcher` into a `Matcher`): a location that is a dir is opened as one (so an existing dir named `a[1]` or `v1.0` is never a pattern); else it is read like a shell reads one word, but not split at spaces (`read_quoted`): `'...'` and `"..."` quote, and `\` escapes (outside quotes anything but an ASCII letter or digit, so a regex's `\d` stays one, and in `"..."` only `"`, `\`, `$` and `` ` ``; never on Windows, where it is a separator), and a quote that is never closed is a plain character. A `~` at the start, before a `/` or nothing, is the home dir (`expand_tilde`), also right after the opening quote (`"~/x"`, which a shell would not expand, but nobody means a dir named `~`; `\~` or `./~` is one); its characters are quoted, and the as-written checks below see it expanded (`Written::until`), so `~/it's/*` works. A quoted character is never special in a pattern: a part is a pattern only if it has an unquoted special character, and quoted special characters are escaped in it (`"[1]"*` is the glob `\[1\]*`), so `Koil::location()` shows it without quotes. Only those special in its kind are (`part_text`): a glob has no `\.`, so `.*\.rs` is the glob `.*.rs`, which a frontend reading the location again as a regex (the app's `:set regex`) gets as the regex `.*.rs`; losing the `\` that way is better than globs showing `\`s they don't need. That only opens names with quotes in them (`it's`, the app shows them as they are) because a dir is first tried as written: the whole location, and each part before a `/` that is not quoted (then the rest is read again from there; a quoted `/` would cut the quotes, and `"a/..` resolves to the dir `"a` is in). `split_location` then works on what was read. Users write only `/`, also on Windows: a plain path with `\` (pasted from Windows) opens as a dir, and `Koil::location()` then shows it with `/` (`with_slashes`, while `current_dir` stays native), so a pattern can be typed after it; in a pattern only `/` (or the root) ends a part, and `\` is an escape (`C:\src\*.rs` is the glob `src\*.rs` in `C:\`). It takes the longest part before a `/` that is a dir, as written or as read (else the root, or `current_dir` for a relative location), then the base dir is everything before the first part with an unquoted special character (`*?[{` for globs, `.,*+?()[]{}|^$\` for regexes), and the rest is `Koil::pattern`, relative to `current_dir` (the base). A glob's `*` never matches `/` (`literal_separator`), `\` escapes (`backslash_escape`, which globset leaves off on Windows), and an option of `{...}` can be empty (`empty_alternates`: `a{,.txt}` is `a` or `a.txt`, as a shell expands it), all set by `glob_builder`. A POSIX class (`[[:digit:]]`), which globset reads as a class of `[:digt` and a `]`, is `GlobError::PosixClass` (`posix_class`, which finds classes with `glob_pieces`, as globset reads them: a `\` in one is a plain character), saying what to write instead (`[0-9]`); a quoted one is no class. While hidden entries are not shown, a glob still shows those that a part starting with a `.` (or `\.`) matches, as a shell does (`Dots`): a hidden name is never matched by a wildcard, but `.*`, `.env{,rc}`, `*/.env` or `**/.env` match it where that part is, and `**` does not go through hidden dirs, so `**/.env` does not enter `.git`. `Dots` reads each glob its braces stand for (`expand_braces`, so `{.env,.envrc}` works too, up to `MAX_EXPANDED`) as its parts between `/`, each compiled on its own, and runs them over a path's names (`Dots::states`, `**` being any number of names that are not hidden), which only paths with a hidden name go through; a path still has to match the glob. A glob with no such part, too many globs in its braces, or a `/` in a class has no `Dots`, and its walk filters hidden entries as before. With `show_hidden`, a wildcard matches them too. A regex must match the whole relative path (wrapped in `^(?:…)$`), and `.*` does match `/`. As a convenience, `expand_commas` turns an unescaped `,` into `[^/]` (any character within one dir level), except inside `[...]` classes and `{...}` repetitions; `\,` is a literal comma. Errors are reported for the regex as written, before the expansion. A pattern view shows every file and dir that matches, a dir matched with a `/` after its path (`Matcher::is_match`), so `,*/` shows only dirs, `.*,` only files, and `**/*` both (`*` can match nothing after the `/`). For a glob, unlike a shell's, that makes `*` show only files, `*/` only dirs, `{*,*/}` both, `src*` not the dir `src`, and `d*/*` the dir `dir` too, as well as what is in it. globset reads `**/` as `**`, so a glob's trailing `/` is taken off and matched apart (`Matcher::Glob`'s `bool`). Names are paths relative to the base (`src/main.rs`). `Koil::location()` is the base, a `/` and the pattern, only with `/` (not for a verbatim `\\?\` path), for frontends to show. A path renamed to something that does not match the pattern leaves the view, but the rename is kept.
- **Views** (`View`, from `Koil::view()`): what the listing shows, a plain dir (direct children) or a pattern (matching files and dirs under the base). `listing`, the diff clearing in `update_entries`, and `list` all go through `View::contains(path, is_dir)`. `list` also adds every changed entry of the diff whose `before` is in the view to `current_listing` (even if hidden), because `update` takes a missing entry of `current_listing` as deleted, and otherwise a rename would become a copy.
- **Apply and undo** (`Koil::apply`/`Koil::undo`, steps in `apply.rs`): `Action::run` moves deletes to the system trash (`trash.rs`; on macOS via `NSFileManager`, since the `trash` crate can not restore there) and returns the `Undo` step that reverts it. A rename to another filesystem (another drive, which `fs::rename` fails on with `CrossesDevices`; a move to an external disk failed on Windows) is `move_across`, as `mv` does it: a copy (`copy` with `moved`, which keeps when each file, dir and link was modified and accessed, set with `filetime`, and a dir's permissions, both after what is in it, and as far as the filesystem keeps them), then the source removed for good (`remove`). A copy that fails is removed again, and so it is if nothing of the source can be removed (a disk that can only be read), so the move changed nothing; if only some of the source is gone, the copy stays, and the error says so. Its undo is the rename back, which goes the same way. `copy` copies a link as a link (on Windows with `symlink_file` or `symlink_dir`, which take a privilege or developer mode, else what a link to a file points to), and fails on a named pipe, a socket or a device, which reading would wait on forever. `Koil` keeps the steps of each apply (and `create_now`) as an `Applied { time, dir, steps }` (`dir` is the open dir then, for a frontend to show paths relative to it), and refreshes afterwards (`Koil::refresh` clears the diff and reopens the dir, IDs are kept; `apply_only` keeps what it did not apply instead, see Picking changes). On a failure the steps that ran can still be undone, and a failed undo keeps the steps it did not run. Undo fails with `KoilError::PendingChanges` while there are unapplied changes (`Koil::has_changes`, from the diff alone, `Diff::is_empty`: an ID only at the path it had changes nothing, which `compute_actions` found by reading the disk and planning).
- **Undo history** (`Koil::history`, `Koil::set_history`, `Koil::undoable`, `Koil::undo_only`): the applies are kept oldest first, and a frontend keeps them across sessions with `set_history` (the GUI in a file every running GUI shares; `Applied` is `Serialize`). `undoable` gives each as an `Undoable { applied, needs, blocked }`, for a frontend to pick from like `changes`: `needs` are the newer applies that changed a path it changed, or one inside it or that it is in (`undo_needs`, by `Undo::paths` and their ancestors), so undoing them first puts back what it changed; `blocked` is the first step that can not run now, with every apply it needs (transitively), newest first, and why (`Blocked`: `Missing`, `Taken`, `NotInTrash`). `apply::check` tells that without running anything, simulating what the steps before do (`Simulated`: a path is looked up through the steps backwards, a move sending it to where it was, and inside a restored dir it is not known, which passes; a `Rename` onto the same file in another case passes, like `Action::run`), and the trash is listed once (`trash::Contents`; on macOS the item's path is checked). A `Trashed` keeps a `stamp` (on macOS the item's `FileKey` in the trash, elsewhere its `time_deleted`), so what is trashed later at its path, once the trash is emptied and the path is free again, is never taken for it (restored in its place). Restoring checks the parent dir only where restoring needs it (`RESTORE_MAKES_PARENTS`: the freedesktop trash makes it). `undo_only(picked)` takes the `Applied`s (not indexes), leaves out a picked one whose needs are not picked (transitively) and ones not in the history anymore, checks them all first (`KoilError::UndoBlocked`, nothing changed), then runs them newest first, and refreshes. `undo` is `undo_only` of the last apply. An apply or undo forgets what `seen` had at the paths it moved away or deleted, and inside them (`unsee`): the file is at another ID's path now, and `sync` never follows a key two IDs were seen with, so a file renamed on disk after koil renamed it was taken for gone and new, and its undo step was not followed.
- **Picking changes** (`Koil::changes`, `Koil::apply_only`, `Koil::discard_only`): `changes` lists what applying would do as `Change { action, needs }`, in the order they run (`planner::order`), but with a rename cycle as its renames, not the steps through a temp path (`a -> b`, `b -> a`, where `compute_actions` gives three), as user wrote them. `needs` (`planner::needs`) are the indexes of the changes it can not be applied without, only directly (a chain of renames would make the whole closure quadratic): the one that removes the path it creates (still taken without it, so a rename onto it fails), and the ones that create a new dir it creates something in (a missing parent too, which is a change of its own, so a dir user leaves picked is created even if empty). The renames of a cycle need each other. A frontend picks what a change needs along with it, and leaves out what needs it. `apply_only(picked)` takes the actions, not indexes, so a change user never saw is never applied; it also leaves out a picked change whose needs are not picked (transitively, `Koil::pick` with `without_unmet`), plans the rest, and runs them (`run_keeping`, which `create_now` shares), and the others stay pending: `Diff::after_steps` takes the steps that ran out of the diff (what they made is not new anymore, what they deleted is gone with what was inside it, a copy made at a temp path first goes where it went) and moves the rest along with them, in order: an ID at a renamed path or inside it follows it, and so does a path written inside a renamed dir (as `Outcome::carried` has it, which is where applying it all would put it), but not one written at the path itself (`a -> z` applied leaves `b -> a` as it is, as the rename freed `a` for it); what was moved into a deleted dir stays where it is (applying it all would trash it), and a create inside it goes. Then `rekey` puts each ID's change under the ID of the path its file is at now (`indexes_of`, which `list` uses too: a path koil knows is always its own ID), and the dir is read again. If a step fails, the steps after it did not run, and stay pending too. `discard_only(picked)` takes the picked changes back without touching the disk (`Diff::without`: a create or copy is not made, a delete or rename stays where it is, a rename with copies is those copies), with every change that needs one (also through others), which could not be applied without it, and reads the dir again; its `Report::changes` is how many it took back. IDs stay as they are, so a frontend can show the listing again as an edit.
- **Creating now** (`Koil::create_steps`, `Koil::create_now`): a new file (or dir) or a copy in the diff can be made on disk before the rest is applied, so a frontend can open a new file to write in it, or a copy to change it apart from what it copies. `create_steps(paths)` is their creates and copies, after the creates of the new dirs they are in (their `needs`, transitively), and the copies of a dir they go in (which the planner runs before them, see below); it fails with `KoilError::NotNew` if the diff does not create or copy to a path, and with `KoilError::NeedsChanges` if anything one needs is not a `CreateDir` or a `Copy` (a rename or delete that frees its path, a dir renamed to its parent), since keeping the other changes pending after those would mean moving IDs. `create_now(paths)` runs them (`run_keeping`, shared with `apply_only`, so they are an undo step like an apply's, and what was made is taken out of the diff: a new path out of `without_id`, a missing parent is not in the diff, and a copy's path out of its ID's afters), so every other change stays, and the dir is read again, so what was made gets IDs (a copy its own). A copy is of what is on disk when it is made, so what changes in a file before the rest is applied, a copy of it applying makes gets too: `copied_from(path)` is the file a copy at `path` is of, which a frontend copies now rather than open (what user changed in it would go to the file it copies, and to the copy), and `copies_of(path)` the copies of `path` or of a dir it is in, which a frontend makes now before it lets user change `path`.
- **`Koil::save_state`/`load_state`** save the whole session as JSON (the undo history too), so another process can continue it. Every path in koil's JSON (the state, `Applied`, `Conflict`, `Entry`) goes through `serde_path`: a string if it is Unicode, as serde keeps one (so what was saved before reads the same), else serde's form of an `OsString` (`{"Unix": [bytes]}`, `{"Windows": [units]}`), where serde's own fails (`save_state` panicked, and a frontend's history stopped being saved). `#[serde(with = "serde_path")]` on a path, `serde_path::option` on an `Option`, `serde_path::many` on a `Vec` or `HashSet`; the diff's `without_id` is saved as pairs, as a path that is not Unicode can not be a JSON key. What `sync` needs to find moved files (`seen`, `dirs_seen`) is not saved: after a load, it finds only those it read again.
- **Changes on disk** (`sync.rs`): `Koil::sync(entries)` reads the open view again, while the user edits `entries` (their listing, not given to `update` yet), and returns `Synced { edits, conflicts, moved, warning }`. It runs on a clone, so a failed read changes nothing.
  - *Finding moved files*: `list` (for `open`, `reopen` and `sync`) records what each walked path is (`seen`: a `FileKey`, and the `Metadata` sorting uses, with whether it is a dir; the key is device, inode and birth time on Unix, as ext4 gives a new file a just deleted inode; creation time and kind on Windows, whose file index needs the file opened), and `dirs_seen` for the open dir and its ancestors. The IDs `sync` tracks are `current_listing`, the IDs in `entries` and the diff's. One that is not where it was (not walked, if it was listed, else not on disk) is matched by key to a walked path koil does not know, else searched for `near` the dir it was in (that dir, the dirs inside it if at most `NEAR_DIRS`, and the dir above), as a file manager renames, moves into a folder, or up. A path koil knows is always its own ID (a file replaced by an atomic save keeps its entry), so only unknown paths match. A key that two files share is never followed (`shared`): one two files in `seen` have, two new paths in the view, or two in a dir searched near. Hard links share one, and on Windows so do files made in the same tick of the clock (a checkout, an unzip), whose creation times are the same: a deleted file was taken as moved into an unrelated file made with it. `repoint` makes everything under the old path follow (`ids`, but not onto a path another ID has; the open dir; the diff's paths, so changes inside a renamed dir follow it; undo steps). `follow_dir` does the same for the open dir (or an ancestor) renamed in its parent, searching the parent; if it is gone, its closest parent opens (`moved`, `Warning::DirNotFound`), and so does a pattern's base over `Limits` (`Warning::OverLimit`).
  - *Intent*: per tracked ID, the paths the user put it at (`targets`: its entries, the diff's afters outside the view, and its own path for one written here from another dir, as `update` keeps the original), and whether it `stays`. Only the IDs whose own file moved (`direct`) can conflict; one carried by a moved dir keeps the user's changes, which followed it.
  - *Edits* (`Edit::Add`, `Remove`, `Change { from, to }`, finding entries by ID and name, as given): an ID that stays follows its file (its entries with the old name change, or go if it left the view, and an ID in `current_listing` with no entry gets one, else the next update deletes it); a gone one's entries go; a new path is added, or a new entry the user wrote at it (same kind) gets its ID. A path that changed kind changes its entry's `/`.
  - *Conflicts*, each left as the safe way until `resolve` takes the other: `Deleted` (deleted, but renamed on disk: kept, so nothing is deleted under a name the user never saw; resolve deletes), `Renamed` (renamed both ways: the user's kept, from the new path; resolve keeps the disk's, making the user's first path it and the rest copies), `Gone` (renamed or copied, but gone: dropped; resolve creates them new and empty), `Taken` (something appeared where the user wrote another entry: both kept, which `update` rejects as a duplicate; resolve deletes the new one). `update` reads a renamed ID left out of the view as a copy, so `sync` adds a diff entry for it (and a kept original as an after).
  - `Koil::watched()` gives what a frontend's file watcher watches (`Watched::dirs`: the open dir, recursive for a pattern, its parent so its rename is seen, the dirs of the diff's befores outside the view), and `Watched::affects(path)`, which the watcher's thread uses to skip events that can not change what `sync` finds (a pattern's uses `Prune` for dirs that could hold matches).

## Architecture

The pipeline is `Koil::update` → the `Diff` accumulator → `Diff::compute_actions` → `planner::plan_actions`.

- **Modules**: `lib.rs` has `Koil` (its fields, most of its API, and `update_entries`) and the types it takes and returns. The rest are child modules, which add to `impl Koil` and use its private fields, and what one module uses from another is `pub(crate)` (the root re-exports the public types): `sort.rs` (`Sort`, `SortBy`, `Metadata`, `disk_size`, `Koil::compare`, `metadata` and `order`), `location.rs` (reading a written location: `read_quoted`, `location_in`, `Koil::read_location`, `split_location` and `complete`, and `resolve`), `pattern.rs` (`Pattern`, `Limits`, `View`, `Matcher`, `Prune`, `Dots`, `walker` and `Koil::walk`), `error.rs` (every error and warning type), `serde_path.rs` (how paths are kept in JSON, see `save_state`), `drives.rs` (see Drives above), and `sync.rs` (see Changes on disk above).
- **`lib.rs` / `Koil`** is built with `typed-builder` (`Koil::builder().ignore(path).build()`). It keeps a stable, append-only `ids: Vec<PathBuf>` table, so every path seen in any opened directory keeps its ID across navigation. `current_listing` holds the ID indexes shown for `current_dir`.
- **Entry names** are checked by `relative_path`: empty and absolute names, names starting with a drive (`C:A` on Windows, which `join` would put on that drive), and names with a `.` or `..` part (split at `\` too on Windows), are rejected. Missing parents of nested names are **not** stored in the diff: `Diff::missing_parents` derives them (dirs that are not on disk, not created, and not a rename/copy target, with something new inside; a file that is moved away or deleted counts as not on disk, `gone_files`, so renaming `file` away and writing `file/x` makes a dir `file`), `compute_actions` creates them, and `listing` shows them as new dirs. So removing the last thing inside a new dir also removes the dir. `check_parents` only rejects a parent that is a file (on disk and not moved away or deleted, or one the diff makes a file: new, renamed or copied there).
- **Edits**: duplicating an ID means copy. Removing it means delete. Changing its name means rename. Writing an ID in a different directory's listing means a move.
- **Cross-directory edits**: `Diff` builds up across several listings. `update_entries` first drops the diff entries that belong to the current directory and rebuilds them from the new edit. It leaves entries from other directories alone.
- **`diff.rs`**: `with_id` maps an ID index to `(before_path, after_paths)`, and `without_id` maps a path to `is_dir` for creates. `compute_actions` handles it like this: no afters means delete; if `before` is still among the afters, the other afters are copies; otherwise one after becomes the rename target and the rest become copies. `Diff::outcome` sums up what it does to its paths, for `update_entries` to check written paths against the rest of the diff.
- **`planner.rs`** (`plan_actions`, `order` for the groups before cycles are broken, `needs`) orders the actions using the `Action::removes/creates/depends_on` relations. It finds what runs after what by path (`Successors`: maps of the paths actions remove and create, as comparing every two actions took 14 s for 10,000 deletes), groups actions into SCCs (`pathfinding`), topologically sorts the groups, and breaks each cycle through a temp path (`.name.koil0`, `.name.koil1`, …), then plans the rest of it again (`break_at`): a cycle of renames next to its first renamed file, and a dir replaced by one inside it (delete or rename `a`, move `a/x` to `a`, which was an assert's panic) by moving (or copying) the deepest such source out first, next to the outermost dir removed around it. Whatever puts a path inside a dir that is removed (renamed or deleted) runs first, a move or copy as a new file does: the path is in the old dir, which takes it along (a move or copy into a renamed dir ran after it by the actions' order alone, and failed). A file has nothing inside, so what goes inside one that is removed goes in the new dir made there, after it: `order`, `needs` and `plan_actions` take an `is_dir` closure for whether a renamed path is a dir (`removed_files`; a delete's kind is in its action), `Path::is_dir` in `Koil`. A copy of a dir runs before every change inside it (`Successors::of`), so it is of the dir as it is on disk, as `create_now` makes it, not as the changes leave it (deletes and renames inside used to run first, creates after, by the actions' order alone); one that something inside its source goes before (moving what is at the copy's path into the dir) is copied to a temp path first, next to where it goes, or to its source if the cycle makes the dir it goes in. A cycle no diff makes is run unbroken (and fails), and breaks are capped, so actions that are not a diff's never panic or loop. `plan_actions` takes an `exists` closure to skip names already on disk; tests pass `|_| false` via a local `plan_actions` wrapper in `test_planner.rs`, which (like its `order` and `needs` wrappers) also passes `|_| true` for `is_dir`, so what is put inside a renamed path is inside the old one. Both helpers sort their output so results are **deterministic**, and the tests depend on exact ordering.

## Tests

- `src/tests/mod.rs` holds the shared helpers: `add`, `delete`, `rename` and `copy` for building `Action`s, and `with_id(id, name)`, `without_id(name)`, `id(koil, name)` and `keep(koil, name)` for building `Entry`s (a trailing `/` in `name` marks a dir). The tests compare against exact `Vec<Action>` ordering.
- Each test file covers one module: `test_diff.rs` (`diff.rs` only, with a hand-built `Diff`), `test_planner.rs` (`planner.rs`), `test_names.rs` (`names::check`), `test_koil.rs` (everything through `Koil`: `open`, `update`, `listing`, errors), `test_sort.rs` (the listing's order, `compare` and `metadata`, in a `tempfile` dir whose files get set times), `test_apply.rs` (`apply.rs`/`trash.rs`: runs the actions on a real `tempfile` dir, then undoes them and compares snapshots of the dir; `check_picked` applies some, checks what is left with `actions_left`, discards it and undoes; these move files to the real system trash; `move_across` is run within one filesystem, and a move through `Koil` to another one where `other_filesystem` finds one: `/dev/shm` on Linux, the build's `target` on CI's Windows, whose temp dir is on another drive, or the dir in `KOIL_TEST_OTHER_FILESYSTEM`, like a disk image mounted with `hdiutil` on macOS, where the test otherwise does nothing), and `test_sync.rs` (`sync.rs`: changes a `tempfile` dir on disk with `fs`, then syncs, and checks the edits, conflicts, resolutions and the actions an update gives after; it makes files with `write` and `mkdir`, which give each its own creation time on Windows, `own_key`, as ones made in the same tick share a key there, and a test that follows a move then fails now and then on CI).
- `test_koil.rs` has the shared helpers `test_path`, `test_koil()`, `test_dir_listing(koil)`, `update_test_dir(extra)`, `diff(koil, ...)` and `errors(result)`, all based on `$CARGO_MANIFEST_DIR/test_dir`. That fixture directory is real (`dir/inside`, `.hidden`, `file`, `file2`, `qwerty`; `.hidden` is only in the listing of `hidden_koil()`) because `compute_actions` calls `is_dir()` on the filesystem, so don't delete or rename it.
- Tests build `Entry`s directly, never listing text. Multi-line strings in tests (if any) are written one line per source line, as `"\` followed by `line\n\` rows.
